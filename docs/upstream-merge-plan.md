# 一、目标

**把本地拨到 upstream latest，处理掉全部代码 / 语义 / 功能 / 效果层面的冲突，同时完整保留本地已有的能力。**

拆成五条可验收的子目标：

| # | 目标 | 验收标准 |
|---|---|---|
| G1 | 不丢本地功能 | 多运行时、模型切换、飞书能力、执行轨迹、离线能力、脚本任务全部照常 |
| G2 | 不丢数据、不错扣 | 凭据完好、配额口径正确、用量归因可查 |
| G3 | 三条运行时功能对等 | 除三个结构性不可能项外，Claude / Codex / Grok 行为一致 |
| G4 | 吸收 upstream 的实质增量 | 新能力接进来且三条运行时都能用 |
| G5 | 降低未来合并成本 | 分叉面收敛，有 CI 兜底，文档不再漂移 |

**"结构性不可能对等"的三项**（明确标注为 Claude-only，不假装）：Workflow 可视化 · 后台任务挂流 · subagent 运行时契约。

## 2.0.1 台账内部的两处矛盾（设计阶段发现，已裁定）

```
连接      IMConnectionManager 按 (userId, channel) 持有一条
路由      registered_groups.folder + target_main_jid
```

一个用户每个渠道只能有一条连接。

## 3.2 目标形态

```
channel_accounts      一行 = 一个 (用户, 渠道, 账号)，可以有多个
channel_mounts        这个聊天挂在哪个账号上、路由到哪个工作区
JID                   feishu:oc_xxx#account:{id}    ← 只有第二个账号起才带片段
```

## 3.3 关键设计：不重写历史 JID

**这是整个方案里最重要的一个决定。**

朴素做法是给所有历史 JID 加账号片段 —— 那要重写 13741 条消息的 `chat_jid`、64 行注册记录、所有绑定引用。不可逆、风险高。

**改成：默认账号隐式化。**

```
没有 #account: 片段的 JID  ≡  属于该渠道的默认账号
有片段的                    ≡  属于指定账号
```

迁移只做两件事：

1. 从 7 份现有配置文件各建一行 `channel_accounts`，标记 `is_default = true`
2. 回填 `registered_groups.channel_account_id`（**加一列，不改 jid**）

**历史 JID 一个字节都不动。** 消息表完全不碰。

只有当你给某个渠道加**第二个**账号时，那个账号的新会话才会带片段。

## 3.4 凭据存储：保留文件加密，改按账号 id 寻址

不把凭据搬进数据库。现有的 AES-256-GCM 文件加密继续用，只改路径：

```
现在   data/config/user-im/{userId}/feishu.json
之后   data/config/user-im/{userId}/accounts/{accountId}/feishu.json
       并保留原路径作为默认账号的软链或副本，直到迁移验证通过
```

理由：加密方案不变 = 风险面不变。数据库只存账号元数据（名称、渠道、是否默认、启用状态、认证状态），**不存密钥**。

## 3.5 连接管理

`IMConnectionManager` 的键从 `(userId, channel)` 改成 `(userId, channel, accountId)`。默认账号的 accountId 是迁移时生成的稳定 id。

热重连、批量断开、状态推送全部按账号粒度。

## 3.6 前端

upstream 的统一渠道账号管理页取代现在 8 个独立卡片。每个渠道下可以有多个账号，各自有连接状态、配对码、二维码（WhatsApp）、断开/登出。

## 3.7 迁移的可回滚性

| 步骤 | 可逆？ |
|---|---|
| 建 `channel_accounts` 表 | 是（删表） |
| 从配置文件投影出 7 行 | 是（删行，原文件不动） |
| 回填 `channel_account_id` 列 | 是（列置 NULL） |
| 凭据文件路径迁移 | 是（保留原路径副本直到验证通过） |
| JID 格式 | **不涉及**（这就是 3.3 的价值） |

**全程可逆。** 这是拆掉 JID 重写之后换来的。

## 5.5.2 分阶段上线还是攒着一次上

**分阶段上线。** 理由：

- 阶段 1 的三个 bug 修完立刻能验证（人格污染、长任务挂死），跑几天确认无副作用
- 阶段 2 合并主体最不确定，单独上线一段时间才能暴露"编译过了但行为变了"的问题
- 阶段 4 和 5 都涉及数据迁移，攒在一起出问题分不清是谁的

建议节奏：**阶段 1 上线跑 2–3 天 → 阶段 2+3 一起上线跑一周 → 阶段 4 上线跑几天 → 阶段 5 单独上 → 阶段 6 随时**。

阶段 2 和 3 一起上的理由：阶段 3 是修阶段 2 引入的运行时不对等，分开上线会有一段时间 Codex/Grok 是残的。
